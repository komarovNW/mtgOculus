# Безопасность публичного репозитория

Репозиторий и production frontend публичны. Любой код, URL и значение,
попавшее в frontend-сборку, нужно считать доступным всем пользователям.

## Что можно хранить

- `.env.example` только с безопасными placeholder или локальными значениями;
- публичные маршруты API;
- документацию по контрактам без credentials;
- обезличенные синтетические test fixtures.

## Что нельзя коммитить

- `.env.local` и другие `.env.*`, кроме `.env.example`;
- API keys, access/refresh tokens, пароли и cookies;
- private keys, сертификаты и signing secrets;
- дампы базы данных;
- production fixtures с именами, email или другой персональной информацией;
- внутренние панели, логи и stack traces с чувствительными данными.

`.gitignore` защищает типовые env, key/certificate и database-файлы, но это не
заменяет проверку изменений перед commit.

## Frontend не хранит секреты

Переменные Vite с префиксом `VITE_` встраиваются в JavaScript bundle. В них
нельзя хранить секреты. `VITE_API_BASE_URL` допустим: адрес backend всё равно
виден в Network браузера.

## Публичное добавление событий

Форма добавления и `POST /api/v1/admin/tournaments/import` намеренно доступны
всем без авторизации.

Публичный доступ не отменяет серверную защиту от некорректных и чрезмерных
запросов. Backend должен валидировать данные, ограничивать размер и частоту
запросов и не возвращать внутренние ошибки или stack traces.

## Проверка перед публикацией

1. Проверить `git diff --cached`.
2. Убедиться, что новые fixtures синтетические.
3. Запустить поиск credentials и private-key headers по отслеживаемым файлам.
4. Проверить, что production config хранится в настройках хостинга.
5. Если секрет уже попал в Git, сначала отозвать/ротировать его. Удаление файла
   из последнего commit не удаляет значение из истории.

Переписывание Git history требует отдельного согласования со всеми участниками и
force-push. В рамках обычной frontend-задачи оно не выполняется.

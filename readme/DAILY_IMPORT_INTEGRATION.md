# Интеграция загрузки дейликов в Magic Oculus

Документ предназначен для разработчика внешнего сервиса, который хочет
передать накопленные дейлики в Magic Oculus через действующий backend API.

Контракт ниже проверен по frontend-коду и публичным справочникам
**31 июля 2026 года**. Перед массовой загрузкой нужно связаться с
[@komarovNV](https://t.me/komarovNV), согласовать набор событий и подтвердить
актуальный production URL API.

## Коротко

Текущий импорт:

- принимает по одному дейлику за запрос;
- не требует авторизации;
- принимает `multipart/form-data`;
- требует ссылку на страницу события в разделе Tourney на AetherHub;
- сам получает из AetherHub финальные стендинги, раунды и результаты матчей;
- получает список колод отдельным текстовым полем;
- объединяет колоды с участниками по имени либо по порядку финальных мест.

Production endpoint на дату проверки:

```text
POST https://bbani33dmiqrgjm2k8fa.containers.yandexcloud.net/api/v1/admin/tournaments/import
```

## Важное ограничение

Сейчас API **не принимает готовые стендинги и раунды в JSON или файлами**.
Отдельной ручки для массовой загрузки также нет.

Для каждого импортируемого дейлика должна существовать доступная страница
AetherHub вида:

```text
https://aetherhub.com/Tourney/...
```

Если во внешней системе есть только собственные стендинги и матчи, но нет
событий на AetherHub, действующего API недостаточно. Для такой интеграции
сначала потребуется согласовать и реализовать новый backend-контракт.

## Справочники

В запрос нельзя передавать произвольные названия города, клуба и формата.
Нужно использовать существующие ID из справочников Magic Oculus.

### Города

```http
GET /api/v1/cities
```

Пример элемента:

```json
{
  "id": "moscow",
  "name": "Москва",
  "country": "Россия"
}
```

### Клубы города

```http
GET /api/v1/cities/{cityId}/clubs
```

Пример:

```json
{
  "id": "edinorog_moscow",
  "cityId": "moscow",
  "name": "Единорог"
}
```

`clubId` должен принадлежать переданному `cityId`.

### Форматы

```http
GET /api/v1/formats
```

Пример:

```json
{
  "id": "legacy",
  "name": "Legacy"
}
```

Перед импортом следует получать справочники через API, а не хранить их копию
навсегда. Если нужного города, клуба или формата нет, его добавление нужно
согласовать с [@komarovNV](https://t.me/komarovNV).

## Запрос на создание дейлика

### Метод и формат

```http
POST /api/v1/admin/tournaments/import
Content-Type: multipart/form-data
```

`Authorization` сейчас не требуется. Заголовок `Content-Type` с boundary должен
формировать HTTP-клиент; не следует задавать boundary вручную.

### Поля

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `date` | string | да | Дата события в формате `YYYY-MM-DD`. |
| `cityId` | string | да | ID из `GET /cities`. |
| `clubId` | string | да | ID из `GET /cities/{cityId}/clubs`. |
| `tournamentType` | string | да | Для дейлика — строго `daily`. Значение `tournament` используется для крупных турниров. |
| `formatId` | string | да | ID из `GET /formats`. |
| `aetherhubUrl` | string | да | Полная HTTPS-ссылка на страницу Tourney в AetherHub. |
| `playerDecksText` | string | да | По одной колоде на каждую непустую строку. Поддерживаются два режима, описанные ниже. |

Заголовок события, стендинги, раунды и результаты матчей отдельно не
передаются: backend получает или формирует их во время импорта.

### Пример cURL

Значения в примере являются шаблоном. Перед выполнением их нужно заменить
реальными данными события.

```bash
curl --request POST \
  'https://bbani33dmiqrgjm2k8fa.containers.yandexcloud.net/api/v1/admin/tournaments/import' \
  --form 'date=2026-07-24' \
  --form 'cityId=moscow' \
  --form 'clubId=edinorog_moscow' \
  --form 'tournamentType=daily' \
  --form 'formatId=legacy' \
  --form 'aetherhubUrl=https://aetherhub.com/Tourney/RoundTourney/REPLACE_ME' \
  --form $'playerDecksText=Игрок 1 - Lands\nИгрок 2 - UW Phelia\nИгрок 3 - Grixis Reanimator'
```

## Подготовка `playerDecksText`

Режим сопоставления определяется автоматически. Два режима нельзя смешивать в
одном запросе.

### Рекомендуемый режим: игрок и колода

Одна строка:

```text
Имя игрока - Название колоды
```

Пример:

```text
Иван Иванов - Lands
Пётр Петров - UW Phelia
Сергей Сергеев - Grixis Reanimator
```

Правила:

- между именем и колодой нужен дефис, среднее тире или длинное тире;
- с обеих сторон разделителя должны быть пробелы;
- порядок строк не важен;
- участник сопоставляется со стендингами AetherHub по имени;
- один игрок не должен встречаться несколько раз;
- имя и название колоды не могут быть пустыми;
- число строк должно покрывать всех участников;
- небольшая нормализация имени может пройти с предупреждением;
- отсутствующий, лишний или неоднозначно сопоставленный игрок блокирует импорт.

Этот режим безопаснее для автоматической интеграции, потому что привязка не
зависит от порядка строк.

### Режим: только колоды по финальным местам

Пример:

```text
Lands
UW Phelia
Grixis Reanimator
```

Первая строка назначается игроку на первом месте в финальных стендингах
AetherHub, вторая — игроку на втором месте и так далее.

Правила:

- количество непустых строк должно точно совпадать с количеством участников;
- порядок должен точно повторять финальные места AetherHub;
- после импорта привязку следует проверить через detail endpoint;
- backend возвращает предупреждение об использовании позиционного режима.

### Общие правила списка

- пустые строки игнорируются;
- заголовки таблицы, комментарии и другие посторонние строки запрещены;
- одинаковые архетипы нужно всегда называть одинаково;
- нельзя смешивать строки `Игрок - Колода` и строки только с колодами;
- необязательная нумерация поддерживается в виде `1.` или `1)`;
- если нумерация используется, она должна идти подряд от 1 до N без пропусков,
  повторов и перестановок.

Пример допустимой нумерации:

```text
1. Иван Иванов - Lands
2. Пётр Петров - UW Phelia
3. Сергей Сергеев - Grixis Reanimator
```

## Что делает backend

Во время импорта backend:

1. проверяет обязательные поля и связи между справочниками;
2. загружает страницу события AetherHub;
3. извлекает финальные стендинги и результаты всех доступных раундов;
4. проверяет игроков и результаты матчей;
5. сопоставляет `playerDecksText` с участниками;
6. создаёт или переиспользует сущности игроков и колод по своим правилам;
7. сохраняет событие и возвращает его ID;
8. возвращает найденные предупреждения, даже если событие создано.

## Успешный ответ

```json
{
  "success": true,
  "tournament": {
    "id": 145,
    "title": "Legacy Daily 24.07.2026"
  },
  "warnings": [
    {
      "code": "PLAYER_NAME_NORMALIZED",
      "message": "Имя \"Панферов Александр\" сопоставлено с \"Панфёров Александр\".",
      "source": "playerDecksText",
      "rawValue": "Панферов Александр",
      "matchedValue": "Панфёров Александр"
    }
  ]
}
```

`warnings` может отсутствовать или быть пустым массивом. Предупреждения не
отменяют создание события, но их нужно записать в лог и проверить.

После успеха созданное событие можно получить:

```http
GET /api/v1/tournaments/{tournament.id}
```

В ответе следует проверить как минимум:

- дату, город, клуб, тип и формат;
- количество строк в `standings`;
- количество и порядок привязок в `playerDecks`;
- наличие раундов и матчей;
- названия колод у нужных игроков.

Страница события на сайте:

```text
https://magicoculus.ru/tournaments/{tournament.id}
```

## Ошибки и предупреждения

Предпочтительный ответ при невозможности импорта:

```json
{
  "success": false,
  "errors": [
    {
      "code": "DECK_PLAYER_NOT_FOUND_IN_STANDINGS",
      "message": "Игрок \"Колошко Александр\" из списка колод отсутствует в стендингах.",
      "source": "playerDecksText",
      "playerName": "Колошко Александр"
    },
    {
      "code": "INVALID_MATCH_SCORE",
      "message": "Некорректный счёт матча в раунде 5, столе 11.",
      "source": "allRoundsFile",
      "roundNumber": 5,
      "tableNumber": 11,
      "rawValue": "2-1-1"
    }
  ],
  "warnings": []
}
```

Элемент ошибки или предупреждения:

```ts
type ImportFeedbackItem = {
  code: string;
  message: string;
  source?: string;
  playerName?: string;
  roundNumber?: number;
  tableNumber?: number;
  rawValue?: string;
  matchedValue?: string;
};
```

Возможные значения `source`, уже поддержанные интерфейсом:

```text
aetherhubUrl
allRoundsFile
date
playerDecksText
standingsFile
```

Интеграция должна:

- считать импорт успешным только при `success: true`;
- проверять тело ответа даже при HTTP `200`;
- сохранять все `errors`, а не только первый элемент;
- сохранять `warnings` как при успехе, так и при ошибке;
- не повторять запрос с ошибкой валидации без исправления исходных данных;
- не ориентироваться только на текст `message`: для автоматики использовать
  стабильный `code`, а текст сохранять для диагностики.

Для ошибок валидации ожидается HTTP `422`. При этом клиент должен быть готов к
тому, что неуспешный результат с `success: false` временно может прийти и с
HTTP `200`.

## Массовая загрузка

Поскольку bulk endpoint отсутствует, каждое событие отправляется отдельным
запросом.

Рекомендуемый порядок интеграции:

1. получить актуальные ID справочников;
2. подготовить и локально проверить все обязательные поля;
3. отправить одно тестовое событие;
4. проверить созданное событие через `GET /tournaments/{id}`;
5. согласовать результат с владельцем Magic Oculus;
6. только после этого загружать оставшуюся историю;
7. сохранять у себя соответствие внешнего события и `tournament.id`;
8. вести отдельный журнал успешных запросов, ошибок и предупреждений.

### Повторы и сетевые ошибки

В текущем публичном контракте нет:

- `Idempotency-Key`;
- поля с ID события во внешней системе;
- описанного bulk endpoint;
- документированной гарантии автоматического удаления дублей;
- опубликованного лимита запросов.

Поэтому:

- нельзя слепо повторять запрос после timeout или обрыва соединения;
- перед повтором нужно проверить, не появилось ли событие на сайте;
- параллелизм и темп массовой загрузки нужно заранее согласовать;
- интеграция должна хранить статус каждого события и уметь продолжать загрузку
  без повторной отправки уже подтверждённых записей.

## Чеклист одного события

- [ ] Страница Tourney на AetherHub доступна без авторизации.
- [ ] Дата соответствует событию.
- [ ] `cityId`, `clubId` и `formatId` существуют в справочниках.
- [ ] `clubId` относится к выбранному городу.
- [ ] `tournamentType` равен `daily`.
- [ ] В `playerDecksText` нет заголовков и комментариев.
- [ ] Для каждого участника указана ровно одна колода.
- [ ] Названия одинаковых архетипов унифицированы.
- [ ] Получен ответ с `success: true`.
- [ ] Все предупреждения сохранены и проверены.
- [ ] ID созданного события сохранён во внешней системе.
- [ ] Стендинги, раунды и привязки колод проверены через detail endpoint.

## Контакты и изменение контракта

До запуска массового импорта необходимо написать
[@komarovNV](https://t.me/komarovNV), если:

- отсутствует нужный город, клуб или формат;
- нет страниц событий на AetherHub;
- нужна загрузка готовых стендингов и раундов;
- нужна авторизованная интеграция или отдельный ключ;
- требуется защита от дублей или идемпотентная повторная отправка;
- планируется загрузить большой исторический набор.

Общий действующий контракт frontend/backend описан в

Состояние на **5 сентября 2026 года**. Документ даёт контекст для backend-задач:
пользовательские сценарии, необходимые данные и подтверждённые ограничения API.

модель API, а не внутреннее устройство базы данных.

## Что получает пользователь

Magic Oculus помогает игроку готовиться к следующему событию по результатам уже
сыгранных: понять локальное поле, сравнить распространённость и результаты
колод, разобрать собственные матчи и найти результаты знакомых игроков.
Для клуба полезны посещаемость дейликов и активность сообщества. Публичный импорт
позволяет самим участникам пополнять историю.

Ограничение продукта: «все события» означает **все загруженные события**, а не
все реально проведённые турниры города. Без сведений о покрытии источников
падение числа загруженных событий нельзя уверенно называть падением активности.

## Что показываем и чего не хватает

| Экран | Уже показываем | Не показываем / ограничение |
|---|---|---|
| Главная | События, участия, игроки, матчи, колоды; популярность, эффективность, игроки, матчапы, последние события | Нет сравнения с предыдущим периодом, свежести и полноты данных. Рейтинг игроков выбирается среди первых 100 по активности, а не гарантированно всей выборки |
| Дейлики | Список, победитель и колода, средняя посещаемость, рекорд, активный клуб, месячная динамика | Нет уникальных посетителей за период, новых и возвращающихся игроков, покрытия клубов |
| Турниры | Список, размер поля, раунды, матчи, победитель | Максимальный размер определяется среди загруженных строк; нет серверного поиска по названию и общей сводки до пагинации |
| Событие | Стендинги с колодами и тайбрейками, путь победителя, пары, BYE, метагейм, заполненность колод, ссылка на источник при наличии | Отдельной дублирующей вкладки «Колоды» уже нет. Нет статуса проверки импорта и времени обновления |
| Игроки | Поиск, активность, record, winrate, любимая колода, порог выборки, распределения и лидеры | Нет сопоставимой динамики относительно прошлого периода. Часть сортировки работает только по загруженным строкам |
| Игрок | Первые места, record по доступной истории, BYE, любимые колода и формат, частый соперник, месяцы, турниры, колоды, личные встречи, история группами событий | Game winrate приходит, но не показан. Нет серверной оценки полноты истории, отдельного агрегата карьеры и загрузки вкладок по запросу |
| Колоды | Все архетипы, поиск, участия, матчи, record, winrate, достаточная выборка, распределения | Поиск и сортировка по winrate требуют полного списка. Нет роста/падения доли поля и покрытия данных по матчапам в сравнении колод |
| Колода | Доля поля, результаты по событиям, игроки, матчапы, лучшие/худшие незеркальные встречи с выборкой 10+, месяцы | Доля поля требует загрузить остальные колоды. Нет доли поля по месяцам, сравнения периодов, результатов без зеркал как отдельного среза |
| Добавить | AetherHub + список колод, проверка ввода, подробные ошибки и предупреждения | Нет preview импорта, идемпотентного повтора, статуса долгой операции и импорта собственных standings/rounds |
| Дайджест | Скрытая заглушка | Нет статей и редакционного процесса; CMS пока не приоритет |
| Что нового | Локальная история релизов | API не требуется |

Не все неиспользуемые поля нужно выводить. `bestRank`, `averageRank`, очки и
тайбрейки участия доступны в моделях, но общий рейтинг по лучшему месту сильно
зависит от размера события. Очки в таблицах игрока и колоды в основном повторяют
record; тайбрейки полезны в стендингах конкретного турнира. Отдельный рейтинг
«лучший/худший личный соперник» намеренно не показывается. Game winrate полезен
как дополнительная метрика лишь вместе с количеством известных игр и их
покрытием; выдумывать игры из BYE нельзя.

## Как устроены данные

```text
Город → клуб → событие ← формат, тип, дата, ссылка AetherHub
                 ├─ участие: игрок + колода + место + record + тайбрейки
                 └─ раунды → пары: игроки + счёт + победитель + признак BYE

Участия → популярность колод, посещаемость, уникальные игроки
Матчи  → record, winrate, личные встречи, матчапы, месячная динамика
```

- ID игроков, колод и событий в raw API числовые; frontend превращает их в строки.
- Справочники используют строковые ID. Клуб зависит от города.
- Один игрок на двух событиях — два участия и один уникальный игрок.
  Поле `playersCount` у колоды означает участия, а `uniquePlayersCount` — людей.
- Колода здесь — именованный архетип, не список из 60/75 карт. Составов карт и
  sideboard в контракте нет. Цвета и `archetype` nullable.
- `matchesCount` имеет разные продуктовые основания: у игрока учитываются
  подтверждённые BYE, у эффективности колоды нужны реальные матчи без BYE.
- Игроки с известными результатами, пары событий и результаты пилотов колоды
  нельзя складывать в один счётчик: матч представлен с двух сторон у игроков.
- Для пары разных колод A/B победа A зеркальна поражению B; зеркальный матч
  требует отдельного правила учёта. Определения должны находиться в контракте.

Поток: URL → `useDashboardFilters` → TanStack Query → `entities/*/api.ts` →
`client.ts` → внешний API → `backend-mappers.ts` → frontend types → виджеты.
При отсутствии `appliedFilters` API-слой дополнительно получает справочники для
подписей. Это ещё одна причина сделать `appliedFilters` обязательным.

Действующие методы перечислены в [BACKEND_API_HANDOFF.md](BACKEND_API_HANDOFF.md):
`/home`, три списка и их detail, справочники и публичный multipart import.
Общие фильтры: город, клуб, формат, тип, включительный период. Деталь колоды
использует её собственный формат. Любимый формат игрока использует всю карьеру,
поэтому сейчас делается второй detail-запрос без dashboard-фильтров.

## Проверка рабочего API

Выполнены только GET-запросы к публичному API из инструкции интеграции.
Срез: `cityId=moscow&formatId=legacy`. Размеры — байты полученного тела JSON;
время — одиночные наблюдения curl, не p95 и не время открытия страницы.

| Запрос | Наблюдение |
|---|---|
| `/home` | HTTP 200; 78 873 байта; около 1,16 с. 109 событий, 207 колод; `deckMetagame` и `deckPerformance` содержат по 207 строк |
| `/home → topPlayers` | 10 игроков, ни один не проходит продуктовый порог 20 результатов в 5 событиях. Поэтому этот массив сейчас не заменяет дополнительный запрос frontend |
| `/decks?search=__oculus_no_such_deck_20260905__&page=1&page_size=2` | HTTP 200; `count=207`, две обычные строки. Поиск действительно не применяется |
| `/decks/50` | HTTP 200; 37 810 байт; 56 результатов, 25 игроков, 78 матчапов загружаются сразу. `summary.metaShare` отсутствует |
| `/players/32` | HTTP 200; 73 395 байт; summary содержит 106 результатов, история — 108 строк, из них 4 относятся к событиям вне массива участий. После текущего ограничения по участиям остаётся 104 строки |
| Те же detail-ответы | Нет явных счётчиков BYE/неизвестных результатов и метаданных полноты; в проверенной истории игрока `isBye` отсутствует |
| Пагинация | `next` может содержать HTTP URL при исходном HTTPS запросе. Frontend использует наличие `next`, но следующий номер запрашивает через настроенный base URL |

Расхождение истории игрока не позволяет по этому ответу объяснить разницу в два
результата и подтвердить BYE. Исправлять данные должен backend по
исходным данным. Реальные ответы не добавлены в репозиторий как fixtures.

## Какой API нужен следующим

Приоритет и предлагаемые контракты находятся в едином backend backlog:
[BACKEND_DATA_ACCURACY.md](BACKEND_DATA_ACCURACY.md#порядок-работ-после-аудита-2026-09-05).

Первый этап: согласованные результаты и фильтры, настоящий поиск колод,
глобальная сортировка, компактная главная с корректными лидерами. Затем —
агрегаты списков, `metaShare` в detail колоды, агрегат карьеры игрока и отдельная
пагинация вкладок. После этого можно надёжно добавить сравнение периодов,
динамику доли метагейма, прозрачное покрытие данных и активность сообщества.

Обновлённые пути API в backlog — предложения к согласованию с backend, не
утверждение об их наличии. Внутренние технологии и схему хранения выбирает backend.

## Как проверить результат изменений API

Сравнивать ответы на одинаковом срезе, отдельно с холодным и тёплым кэшем:
размер JSON, время ответа, число запросов для получения первой страницы и
полной сводки. Повторить проверку на наборе в 10 раз больше.

После перехода на агрегаты число запросов для первой страницы должно оставаться
постоянным. Сводка не должна зависеть от пагинации, а её счётчики должны сходиться
с полным набором результатов. Подробные критерии — в
[BACKEND_DATA_ACCURACY.md](BACKEND_DATA_ACCURACY.md).

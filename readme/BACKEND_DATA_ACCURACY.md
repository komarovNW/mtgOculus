# Задачи для backend

Документ содержит только те задачи, которые после повторного аудита нельзя
надёжно решить на frontend. Для каждой задачи указано, что требуется и почему
ответственность должна находиться на backend.

Это основное ТЗ для backend-разработчика. Начать с раздела
[«Порядок работ после аудита 2026-09-05»](#порядок-работ-после-аудита-2026-09-05):
в нём указаны приоритеты P0, P1 и P2. Ниже приведены требования к данным,
предложения по контрактам и критерии готовности. Контекст и примеры проблем
можно посмотреть в [PROJECT_AUDIT.md](PROJECT_AUDIT.md).

Здесь не описываются архитектура, технология, схема хранения или внутренний
способ расчёта.

Дополнение от 2026-09-06: для возможности добавлять любые колоды в матрицу
нужны явный состав через `deckIds` в `/matchups` и серверный поиск в `/decks`.
Точный контракт и критерии готовности находятся в отдельном ТЗ
[BACKEND_MATCHUP_SELECTION.md](BACKEND_MATCHUP_SELECTION.md). Эта задача
блокирует ручной выбор колод за пределами топ-40.

## 1. Единая классификация результатов матчей

**Что нужно сделать**

Во всех статистических ответах разделить:

- пары турнира;
- матчи с двумя реальными игроками;
- BYE;
- результаты, тип которых нельзя определить.

В данных турнира нужны:

- `pairingsCount`;
- `playedMatchesCount`;
- `byesCount`;
- `unknownResultsCount`.

В остальных статистических ответах нужны применимые к ним
`playedMatchesCount`, `byesCount` и `unknownResultsCount`.

У каждой строки матча нужен явный признак `isBye`. Отсутствие второго игрока без
этого признака считается неизвестным результатом, а не BYE.

**Почему это нужно делать на backend**

Только backend знает исходный тип записи и видит полный набор результатов.
Frontend не может надёжно отличить BYE от неполных данных. Попытка восстановить
тип по отсутствующему игроку, record или номеру раунда даёт недостоверную
статистику.

## 2. Согласованная статистика матчей

**Что нужно сделать**

Одинаково считать матчи, record и winrate во всех ответах:

- для турниров и колод BYE не входит в сыгранные матчи, record, winrate и
  матчапы;
- в статистике игрока подтверждённый BYE входит в число известных результатов
  и побед;
- неизвестные результаты не входят в record и winrate;
- `matchesCount`, суммы побед, поражений и ничьих не противоречат друг другу.

**Почему это нужно делать на backend**

Эти значения используются на нескольких экранах и по разным срезам данных.
Если каждый экран исправляет их самостоятельно, одинаковый матч начинает
учитываться по-разному. Backend является единственной общей точкой, которая
видит все результаты и может вернуть согласованные агрегаты.

## 3. Полная история матчей игрока, включая BYE

**Что нужно сделать**

История игрока должна содержать все результаты выбранного среза. Подтверждённый
BYE возвращается отдельной строкой с `opponent: null` и `isBye: true`.

Summary, участия в турнирах, статистика колод и история матчей должны относиться
к одному набору событий.

**Почему это нужно делать на backend**

Frontend может видеть больше результатов в summary, чем строк в истории.
В таком случае показывается доступная история и её неполнота. Клиент не
может восстановить отсутствующую строку без риска придумать неверный раунд,
колоду или результат.

## 4. Согласованные данные участника турнира

**Что нужно сделать**

Колода участника должна иметь одинаковые `id` и `name` во всех частях ответа
турнира:

- `standings`;
- игроки в `rounds`;
- `playerDecks`;
- `metagame`;
- колода победителя.

В объекте турнира также нужна исходная ссылка `aetherhubUrl`, если она была
сохранена при импорте.

**Почему это нужно делать на backend**

Frontend не знает, какая из конфликтующих версий колоды является правильной, и
не может восстановить отсутствующую исходную ссылку. Это исходные данные
события, а не представление интерфейса.

## 5. Поиск колод до пагинации

**Что нужно сделать**

Исправить поиск в `GET /decks`. Он должен применяться ко всей выборке до
пагинации и влиять на:

- `results`;
- `count`;
- `next` и `previous`;
- агрегаты найденной выборки.

**Почему это нужно делать на backend**

Frontend получает только одну часть пагинированного списка. Клиентская
фильтрация либо пропускает подходящие строки с незагруженных страниц, либо
требует скачать таблицу целиком и тем самым отменяет смысл пагинации.

## 6. Глобальная сортировка больших списков

**Что нужно сделать**

Сортировка должна применяться ко всей найденной выборке до разбиения на
страницы.

Она нужна для пользовательских колонок:

| Список | Поля |
|---|---|
| Турниры | дата, название, клуб, формат, игроки, раунды, сыгранные матчи, победитель |
| Игроки | имя, турниры, матчи, record, winrate, любимая колода |
| Колоды | название, формат, турниры, участия, матчи, record, winrate |

Порядок должен быть стабильным между страницами.

**Почему это нужно делать на backend**

Frontend может отсортировать только уже загруженные строки. При серверной
пагинации такая сортировка не меняет положение строк на остальных страницах и
показывает пользователю неверный глобальный порядок.

## 7. Агрегаты списка турниров и дейликов

**Что нужно сделать**

Для полной отфильтрованной выборки вернуть:

- последнее событие;
- самое крупное событие;
- для дейликов — среднее число игроков;
- для дейликов — самый активный клуб;
- для дейликов — месячную динамику количества событий и посещаемости.

Значения не должны зависеть от номера или размера текущей страницы.

**Почему это нужно делать на backend**

Для этих показателей нужны все события выбранного периода. Расчёт по загруженной
странице даёт неверный рекорд, среднее и месячную динамику, а загрузка всех
страниц ради нескольких показателей не масштабируется.

## 8. Агрегаты списка игроков

**Что нужно сделать**

Для полной выборки после фильтров и поиска вернуть данные, необходимые текущим
блокам списка:

- самый активный игрок;
- лучший игрок с достаточной выборкой;
- количество и долю игроков с достаточной выборкой;
- медиану турниров и известных результатов;
- долю результатов десяти самых активных игроков;
- распределение игроков по числу турниров;
- пять самых частых любимых колод среди игроков с достаточной выборкой.

Агрегаты не должны зависеть от пагинации или выбранной сортировки таблицы.

**Почему это нужно делать на backend**

Каждый показатель сравнивает игроков из полной найденной выборки. Frontend не
может получить точный результат по одной странице, а текущая загрузка всех
игроков дублирует работу backend и становится дороже с ростом данных.

## 9. Агрегаты списка колод

**Что нужно сделать**

Для полной выборки после фильтров и поиска вернуть:

- самую популярную колоду;
- лучшую колоду с достаточной выборкой;
- пять лучших колод с достаточной выборкой;
- количество и долю колод с достаточной выборкой;
- медиану турниров и матчей;
- долю участий десяти самых популярных колод;
- распределение колод по числу турниров.

Агрегаты не должны зависеть от пагинации или выбранной сортировки таблицы.

**Почему это нужно делать на backend**

Эти показатели требуют сравнить все колоды найденного среза. Расчёт на frontend
сейчас заставляет загружать каждую страницу списка и отдельно повторять поиск и
сортировку в браузере.

## 10. Единое правило достаточной выборки

**Что нужно сделать**

Поле `isSmallSample` и выбор лидеров должны использовать единые продуктовые
пороги:

- общий рейтинг игрока — минимум 20 известных результатов в 5 турнирах;
- общий рейтинг колоды — минимум 30 сыгранных матчей в 10 турнирах;
- сравнение матчапов — минимум 10 сыгранных матчей.

Мягкий порог личной страницы игрока — 5 результатов в 2 событиях — остаётся
отдельным правилом интерфейса и не заменяет порог общего рейтинга.

**Почему это нужно делать на backend**

Backend уже возвращает `isSmallSample` и должен использовать этот признак при
выборе глобальных лидеров до пагинации. Если сервер и клиент применяют разные
пороги, одна сущность одновременно считается устойчивой в одном ответе и малой
выборкой на другом экране.

## 11. Агрегаты detail-страницы игрока

**Что нужно сделать**

По полной истории игрока вернуть:

- количество первых мест;
- любимую колоду и долю результатов на ней;
- самый частый формат за карьеру;
- самого частого реального оппонента;
- первый и последний турнир;
- месячную динамику турниров, результатов, BYE, побед, поражений, ничьих и
  winrate.

Любимый формат за карьеру не должен ограничиваться активным dashboard-фильтром
формата. Остальные показатели должны явно соответствовать выбранному срезу.

**Почему это нужно делать на backend**

Эти показатели требуют полной истории, тогда как сами списки истории должны
загружаться страницами. Без готовых агрегатов frontend вынужден запрашивать
detail второй раз без фильтров и держать всю карьеру игрока в памяти.

## 12. Пагинация больших разделов игрока

**Что нужно сделать**

Отдельно пагинировать:

- турниры игрока;
- статистику игрока по колодам;
- статистику по оппонентам;
- историю матчей.

Фильтры, `count` и глобальная сортировка должны относиться ко всей выборке.
Страницы не должны содержать повторов или пропусков. История не должна
показывать пользователю частично загруженный турнир как полную группу матчей.

**Почему это нужно делать на backend**

Эти разделы растут вместе с карьерой игрока. Скрытие части уже загруженного
массива кнопкой «Показать ещё» не уменьшает ответ API, расход памяти и время
первой загрузки. Только backend может разбить полный набор до передачи клиенту.

## 13. Агрегаты detail-страницы колоды

**Что нужно сделать**

По полной отфильтрованной истории колоды вернуть:

- долю всех участий в метагейме;
- самого активного игрока;
- самый частый матчап;
- лучший и худший незеркальный матчап с достаточной выборкой;
- количество матчей с известной и неизвестной колодой оппонента;
- месячную динамику турниров, участий, матчей, record и winrate.

BYE и неизвестные результаты не должны попадать в матчапы.

**Почему это нужно делать на backend**

Доля метагейма требует общего числа участий всех колод, а выбор лучшего игрока и
матчапа — всех строк соответствующих разделов. После пагинации этих списков
frontend больше не будет иметь полный набор для точного расчёта.

## 14. Пагинация больших разделов колоды

**Что нужно сделать**

Отдельно пагинировать:

- результаты колоды по турнирам;
- игроков колоды;
- матчапы.

Каждый раздел должен учитывать общие фильтры, возвращать общее количество строк
и иметь стабильную глобальную сортировку.

**Почему это нужно делать на backend**

Количество результатов, игроков и матчапов не ограничено размером одного
турнира и постоянно растёт. Клиентская кнопка, которая показывает следующую
часть уже скачанного массива, не является пагинацией данных.

## 15. Компактный ответ главной страницы

**Что нужно сделать**

`GET /home` должен возвращать summary по полной выборке и только короткие,
правильно отсортированные превью:

- последние турниры;
- самые популярные колоды;
- лучшие колоды с достаточной выборкой;
- лучшие игроки с достаточной выборкой;
- самые частые матчапы.

Каждая строка превью должна содержать все данные, необходимые её блоку.
Полные списки остаются в отдельных пагинированных ручках.

**Почему это нужно делать на backend**

Главная показывает не более десяти строк в секции, но текущий ответ может
передавать сотни колод. Frontend отбрасывает большую часть ответа сразу после
загрузки, что увеличивает размер ответа и время обработки без пользы для
пользователя.

## Границы backend-задач

От backend требуются корректные данные, серверные агрегаты, поиск, сортировка,
пагинация и обязательная валидация импорта. Изменение интерфейса и подключение
новых методов выполняются отдельно на frontend. Действующий контракт нужно
сохранять до согласованного переключения клиента.

## Что уже есть на backend

Повторно делать эти задачи не нужно:

- пагинация основных списков через `count`, `next`, `previous` и `results`;
- общие dashboard-фильтры;
- поиск и основная сортировка игроков;
- разделение дейликов и турниров через `tournamentType`;
- summary, record, winrate и `metaShare`;
- `appliedFilters` в статистических ответах;
- справочники городов, клубов и форматов.

При изменениях выше это поведение нужно сохранить.

## Общие критерии готовности

- Переход между страницами не меняет summary и глобальные агрегаты.
- Фильтры и поиск одинаково влияют на строки, `count` и агрегаты.
- Сортировка применяется ко всей выборке, а не к текущей странице.
- Между страницами нет повторов и пропусков.
- BYE не восстанавливается и не угадывается на frontend.
- Большие списки не загружаются целиком ради одного показателя.
- Главная не передаёт полные списки для коротких превью.

### Предложение: агрегаты отдельно от страниц списка

Вариант внешнего контракта:

```text
GET /tournaments/insights + dashboard filters + search
GET /players/insights     + dashboard filters + search
GET /decks/insights       + dashboard filters + search
```

Допустим эквивалентный компактный `insights` в первой странице списка. Существенно,
чтобы агрегат не требовал загрузки остальных страниц, не повторялся большим
объектом в каждой странице и использовал тот же поиск. Сортировка строк не
должна менять его значение. Путь и способ доставки согласуются с backend.

Минимальные группы данных:

| Ресурс | Поля агрегата |
|---|---|
| События | `eventsCount`, `latestEvent`, `largestEvent`, `averageAttendance`, `mostActiveClub`, `monthlyActivity` |
| Игроки | `playersCount`, `mostActivePlayer`, `bestEstablishedPlayer`, `establishedPlayersCount`, `establishedPlayersShare`, `medianTournaments`, `medianResults`, `top10ResultsShare`, `activityDistribution`, `favoriteDecks` |
| Колоды | `decksCount`, `mostPopularDeck`, `bestEstablishedDeck`, `topEstablishedDecks`, `establishedDecksCount`, `establishedDecksShare`, `medianTournaments`, `medianMatches`, `top10ParticipationsShare`, `activityDistribution` |

Строка лидера содержит ID, имя, необходимые счётчики и record, а не только имя.
Ноль событий означает пустые лидеры (`null`), пустые распределения и отсутствие
вычислимых средних (`null`). Доля всегда сопровождается числителем и знаменателем
либо достаточными счётчиками для их восстановления.

В `/decks` и `/players` нужны единые `sort` + `order` и документированные
допустимые значения. При равенстве — стабильный tie-break по ID. При внедрении
новой схемы надо сохранить текущие значения сортировки колод или согласовать
миграцию. Для нового поиска событий требуются title/search и поиск до пагинации.

### Предложение: компактные detail и независимые вкладки

```text
GET /players/{id}              → identity + scoped summary + insights + counts
GET /players/{id}/career       → любимый формат, начало/конец карьеры; без dashboard filters
GET /players/{id}/tournaments  → пагинация участий
GET /players/{id}/decks        → пагинация результатов по колодам
GET /players/{id}/opponents    → пагинация личных встреч
GET /players/{id}/match-history → пагинация целых групп событий

GET /decks/{id}                → identity + scoped summary + insights + counts
GET /decks/{id}/results        → пагинация участий
GET /decks/{id}/players        → пагинация пилотов
GET /decks/{id}/matchups       → пагинация матчапов
```

Detail колоды возвращает `summary.metaShare` и общий знаменатель
`metagameParticipationsCount`. Нельзя использовать количество только известных
колод как полный объём поля без отдельного обозначения покрытия.
Detail игрока может включать компактный `career` вместо отдельного endpoint,
если это не увеличивает стоимость каждого запроса. Его область явно `career`;
любимая колода и частый оппонент остаются в выбранном срезе.

История матчей возвращает `count` **событий**, `matchesCount` всей истории и
`results: [{ tournament, record, isComplete, matches: [...] }]`. Страница не
обрывает группу события. В каждой строке нужен стабильный `matchId`; ссылки и
метаданные события можно хранить в заголовке группы без повторения в каждом матче.
`isComplete` показывает полноту импорта этого события, не факт получения страницы.

Месячная история приходит как агрегат отдельно от строк вкладок. Количество
событий, участников и результатов не должно вычисляться по первой странице.
Для колоды нельзя строить месячный record из standings игрока, включающих BYE.

### Уточнение к компактной главной

Лимиты превью применяются **после** сортировки и проверки достаточной выборки.
Для `deckPerformance` нужен собственный `tournamentsCount`: сейчас frontend
достаёт его из полного `deckMetagame`. Удаление полной меты без этого поля
может убрать из рейтинга сильную, но менее популярную колоду.

Рядом с top-N метагейма нужен остаток `otherParticipationsCount`/`otherMetaShare`
и отдельное покрытие неизвестных колод. Усечение массива не должно превращать
10 популярных колод в 100% поля или терять категорию «Другие». Все доли имеют
тот же знаменатель, что summary. Аналогично лидеры в `HomeHighlights` должны
получаться из явных агрегатов, если их больше нельзя найти в коротких превью.

## 16. Полнота и свежесть статистики

**Что нужно:** общие метаданные статистических ответов:

```ts
type DataContext = {
  generatedAt: string;             // время формирования ответа
  dataUpdatedAt: string | null;    // время последнего изменения исходных данных
  snapshotId: string;              // согласованный набор данных для страниц
  appliedFilters: AppliedFilters;
  coverage: {
    knownDeckParticipations: number;
    totalParticipations: number;
    playedMatchesCount: number;
    byesCount: number;
    unknownResultsCount: number;
    isMatchHistoryComplete: boolean | null;
  };
};
```

Это иллюстрация: применимость полей зависит от ресурса. `generatedAt` не заменяет
свежесть исходных данных. Отсутствие знания о полноте должно быть `null`/unknown,
а не `true`. `appliedFilters` обязательно отражает принятый сервером срез.

**Почему backend:** только сервер знает импортированные события, изменения,
пропущенные строки и согласованность разных страниц. При изменении набора между
страницами нужен документированный способ продолжить снимок либо начать заново.
Кэш и условные GET с ETag должны учитывать весь срез; после импорта изменяются
версия данных и затронутые агрегаты. Конкретный механизм кэширования не задан.

**Польза:** подпись «обновлено…», доля известных колод, понятное объяснение
неполной статистики; повторные открытия не передают неизменившийся JSON.

## 17. Сравнение сопоставимых периодов

**Предложение:** `/analytics/comparison` с dashboard filters, текущим и базовым
периодами. Для страницы колоды/игрока возможен эквивалентный scoped endpoint.

Ответ содержит оба фактических периода, события, участия, реальные матчи,
record, winrate и метаданные покрытия отдельно для каждого периода. Для колод
нужны доля поля, изменение доли и изменение winrate в **процентных пунктах**.
Если базовый знаменатель равен нулю, относительное изменение — `null`, а не 0%.
Нельзя усреднять проценты турниров: процент считается из общих W/L/D.

Сравнение по умолчанию требует двух законченных интервалов равной длины.
Текущий незаконченный месяц нельзя незаметно сравнивать с целым предыдущим.
При падении покрытия импорта показывается ограничение вывода. Это описательная
динамика, а не доказательство изменения силы колоды или навыка игрока.

**Почему backend:** два полных среза, одинаковые правила учёта и известная
полнота. Пользователь видит, какие колоды набирают популярность и как изменились
его результаты, без повторной загрузки всей истории в браузер.

## 18. Динамика метагейма и качество матчапов

**Предложение:** `/analytics/metagame/history?granularity=month` с dashboard
filters и ограниченным набором `deckIds`. Возвращаются периоды, участия каждой
колоды, общий знаменатель, доля поля, record реальных матчей и покрытие.
Месяц без событий отличается от месяца с событиями без указанной колоды.

Для `/decks/{id}/matchups` полезны `lastPlayedAt`, число разных пилотов и
событий, явный `isMirror`, покрытие известных оппонентов. При сравнении результата
колоды полезен отдельный record без зеркал с явным названием основания.
Нельзя выводить силу архетипа только из 10 матчей одного пилота без подписи размера
и состава выборки. Интервал неопределённости возможен после согласования метода;
он не доказывает независимость матчей одного игрока.

**Почему backend:** нужны все встречи выбранного периода и корректное
различение физических матчей и результатов пилотов, особенно в зеркале.

## 19. Новые и возвращающиеся участники сообщества

**Что нужно:** в агрегате дейликов/клуба — уникальные игроки, число первых
появлений и повторных посещений, помесячные участия. «Новый» определяется как
первое **известное сервису** участие в явно заданной области (город/клуб/формат).
Фильтр периода не должен скрывать более ранние появления при этой проверке.

**Почему backend:** сумма участников событий не равна уникальным людям,
а статус нового участника требует истории до выбранного периода. Польза —
понимание размера и регулярности сообщества, без публикации дополнительных
персональных данных или списка «переставших ходить» игроков.

## 20. Игровые результаты с известным покрытием

**Что нужно:** дополнить уже существующие `gameWins`, `gameLosses`, `gameDraws`,
`gameWinRate` количеством матчей с известным игровым счётом. BYE не создаёт
два выигранных гейма. Для колоды определить то же основание, а при отсутствии
игрового счёта возвращать `null`, не ноль. Отдельно проверять счёт формата best-of.

**Почему backend:** исходный счёт может отсутствовать или отличаться от
технического результата матча. После проверки поле можно показать компактно
в дополнительной статистике игрока, не перегружая основной экран.

## 21. Проверяемый импорт и безопасный повтор

**Что нужно:** результат проверки до сохранения с распознанными участниками,
колодами и проблемами; стабильный идентификатор импорта/источника; идемпотентный
повтор и возможность узнать статус после timeout. Например,
`POST /admin/tournaments/import/preview`, `GET /admin/tournaments/imports/{id}`
и согласованный `Idempotency-Key` для подтверждённого создания.

**Почему backend:** браузер не знает, завершилась ли транзакция после обрыва
связи, и не может гарантировать отсутствие дублей. Preview не должен создавать
турнир. Повтор с тем же ключом и другим телом возвращает понятный конфликт.
При успехе возвращаются ID события, источник, предупреждения и версия данных.
Публичность формы сохраняется.

## Переход без поломки действующего frontend

1. Сначала исправить данные и добавить согласованные агрегаты, не удаляя поля.
2. Зафиксировать контракт/версию или явную возможность нового ответа. Отсутствие
   необязательного поля не должно трактоваться как нулевая статистика.
3. Сверить агрегаты с полным набором на маленьких синтетических примерах, включая
   BYE, неизвестный результат, зеркало, нулевой период, ничью, разные клубы,
   результаты за границей периода и лидера на последней странице.
4. Передать frontend-разработчику готовые контракты и примеры ответов. Сохранить
   старые поля и полные массивы до подтверждения, что клиент переключён на новые
   методы. Подключение API и удаление клиентских обходных решений — отдельная
   frontend-задача.
5. Проверить поиск/сортировку по последней странице, равенство агрегатов на разных
   страницах и отсутствие дублей при добавлении события между запросами.
6. Сравнить число запросов и размер первой загрузки на обычном и увеличенном
   наборе. Цель: один компактный `/home`; для списка — первая страница + агрегат;
   для detail — сводка + активная вкладка. Справочники кэшируются отдельно.

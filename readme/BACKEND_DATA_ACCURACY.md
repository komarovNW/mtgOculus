# Требования к данным и пагинации

## Задача

Frontend не должен получать неполные данные и затем выдавать их за статистику по
всей выборке. От backend нужны готовые агрегаты и пагинация больших списков.

Способ реализации, структура базы данных и оптимизация остаются на усмотрение
backend.

## Приоритет 1. «Быстрый ориентир» в списках

Добавить готовые `insights` в:

- `GET /api/v1/tournaments`;
- `GET /api/v1/players`;
- `GET /api/v1/decks`.

Полный список полей и правил:
[BACKEND_LIST_INSIGHTS.md](BACKEND_LIST_INSIGHTS.md).

Главное требование: значения рассчитываются по всей отфильтрованной выборке и не
зависят от текущей страницы.

## Приоритет 2. Статистика игрока

Frontendу нужны готовые данные по всей истории игрока:

- любимый формат;
- самый частый оппонент;
- количество реальных матчей;
- количество BYE.

Эти значения не должны рассчитываться из одной страницы истории матчей.

### Любимый формат

Нужны:

- `format`;
- `matchesCount`;
- `tournamentsCount`.

Правила:

- учитывается вся доступная карьера игрока;
- главным показателем является количество реальных матчей;
- при равенстве учитывается количество турниров, затем название формата;
- dashboard-фильтр `formatId` не должен превращать любимый формат в заранее
  известное значение;
- если данных нет, возвращается `null`.

### Самый частый оппонент

Нужны:

- `player`;
- `matchesCount`;
- `wins`;
- `losses`;
- `draws`;
- `winRate`.

Правила:

- учитываются только матчи с реальным оппонентом;
- BYE не участвует;
- главным показателем является количество личных матчей;
- при равенстве учитываются победы, затем имя и `id` оппонента;
- если данных нет, возвращается `null`.

### Матчи и BYE

В summary игрока нужны отдельные поля:

```json
{
  "matchesCount": 0,
  "playedMatchesCount": 0,
  "byesCount": 0
}
```

Требования:

- `playedMatchesCount` считает только матчи с реальным оппонентом;
- `byesCount` считает BYE;
- backend должен однозначно определить, входит ли BYE в `matchesCount` и
  `matchWins`;
- одинаковые определения используются во всех ответах API.

## Приоритет 3. История матчей игрока

История матчей должна загружаться страницами.

Ожидаемый запрос:

```http
GET /api/v1/players/{id}/matches?page=1&page_size=50
```

Требования:

- поддерживаются общие dashboard-фильтры;
- ответ содержит `count`, `next`, `previous`, `appliedFilters` и `results`;
- в `results` находятся только матчи с реальным оппонентом;
- строки содержат событие, раунд, стол, обе колоды, оппонента, счёт и результат;
- по умолчанию сначала показываются новые события и поздние раунды;
- между страницами нет повторов и пропусков;
- пагинация истории не меняет summary и insights игрока.

## Приоритет 4. Серверная сортировка списков

Пагинированные списки должны сортироваться целиком, а не только внутри одной
страницы.

Общие параметры:

```text
sort=<field>
order=asc|desc
```

Нужные поля сортировки:

| Список | Поля |
|---|---|
| Турниры | `date`, `title`, `playersCount`, `roundsCount`, `matchesCount`, `winnerName` |
| Игроки | `name`, `tournamentsCount`, `matchesCount`, `matchWins`, `matchWinRate`, `bestRank`, `mostPlayedDeck` |
| Колоды | `name`, `format`, `tournamentsCount`, `playersCount`, `matchesCount`, `matchWins`, `matchWinRate`, `bestRank` |

Требования:

- одинаковый запрос всегда возвращает стабильный порядок;
- соседние страницы не содержат повторов и пропусков;
- неизвестное поле сортировки возвращает понятную ошибку `400`;
- `count` учитывает фильтры и поиск, но не пагинацию.

## Приоритет 5. Размер больших ответов

### Главная

`GET /api/v1/home` не должен возвращать сотни строк в секциях, где интерфейс
показывает только первые 10.

От backend нужны:

- summary по всей выборке;
- отдельные готовые highlights;
- не более 10 строк в превью-секциях.

Полные списки пользователь открывает на страницах турниров, игроков и колод.

### Страница колоды

Большие списки результатов, игроков и матчапов должны поддерживать пагинацию:

```http
GET /api/v1/decks/{id}/tournaments
GET /api/v1/decks/{id}/players
GET /api/v1/decks/{id}/matchups
```

Каждый список:

- принимает общие фильтры;
- возвращает `count`, `next`, `previous` и `results`;
- сортирует всю выборку;
- не меняет общий summary колоды;
- для матчапов использует статистику по всей выбранной выборке до пагинации.

## Что уже есть и не требует отдельной задачи

- общее количество сущностей уже приходит в `count`;
- поиск игроков и колод уже выполняется на backend;
- дейлики и турниры уже разделяются через `tournamentType`;
- существующие summary, record и winrate не нужно дублировать отдельными
  запросами.

## Не входит в текущую задачу

- API для дайджеста;
- лучший и худший личный winrate игрока против оппонентов;
- публичный импорт событий;
- выбор конкретной технологии, схемы базы данных или способа кэширования.

## Готово, когда

- [ ] Глобальные показатели не меняются после `Показать ещё`.
- [ ] Любимый формат и частый оппонент не зависят от страницы истории матчей.
- [ ] BYE отделены от матчей с реальным оппонентом.
- [ ] История большого игрока загружается страницами.
- [ ] Сортировка применяется ко всей выборке.
- [ ] Между страницами нет повторов и пропусков.
- [ ] Главная не возвращает сотни строк для коротких превью.
- [ ] Большие списки на странице колоды можно загружать частями.

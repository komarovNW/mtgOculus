# Требования к данным и пагинации

## Задача

Frontend не должен получать неполные данные и затем выдавать их за статистику по
всей выборке. От backend нужны готовые агрегаты и пагинация больших списков.

Способ реализации, структура базы данных и оптимизация остаются на усмотрение
backend.

## Приоритет 1. «Быстрый ориентир» в списках

Добавить готовые `insights` в:

- `GET /api/v1/tournaments`;
- `GET /api/v1/players`;
- `GET /api/v1/decks`.

Полный список полей и правил:
[BACKEND_LIST_INSIGHTS.md](BACKEND_LIST_INSIGHTS.md).

Главное требование: значения рассчитываются по всей отфильтрованной выборке и не
зависят от текущей страницы.

## Приоритет 2. Данные отдельного турнира

Для `GET /api/v1/tournaments/{id}` нужны согласованные данные события.

### Матчи и BYE

В объекте турнира нужны отдельные поля:

```json
{
  "pairingsCount": 0,
  "playedMatchesCount": 0,
  "byesCount": 0,
  "unknownResultsCount": 0
}
```

Требования:

- `playedMatchesCount` считает только матчи с двумя реальными игроками;
- `byesCount` считает технические пары с BYE;
- `pairingsCount` равен сумме сыгранных матчей и BYE;
- у каждой строки раунда поле `isBye` обязательно;
- отсутствие второго игрока само по себе не означает BYE;
- если тип записи определить нельзя, она относится к `unknownResultsCount` и
  не участвует в статистике;
- BYE не участвует в статистике матчапов и винрейтах;
- в личной статистике игрока BYE при этом учитывается как победа;

### Колода участника

Колода одного участника должна иметь одинаковые `id` и `name` во всех частях
ответа:

- `standings`;
- `rounds.playerA.deck` и `rounds.playerB.deck`;
- `playerDecks`;
- `metagame`;
- `tournament.winner.deck`.

### Источник события

В объекте турнира нужно поле:

```json
{
  "aetherhubUrl": "https://aetherhub.com/Tourney/RoundTourney/..."
}
```

Frontend использует его для ссылки на исходную страницу события.

## Приоритет 3. Статистика игрока

В `GET /api/v1/players/{id}` нужен объект `insights` по полной истории игрока:

- любимый формат;
- любимая колода;
- самый частый оппонент;
- количество побед в турнирах — финишей на первом месте;
- количество известных матчей, включая BYE;
- количество BYE;
- динамика по месяцам: турниры, известные матчи, победы, поражения, ничьи и
  процент побед.

Эти значения не должны рассчитываться из одной страницы истории матчей.

`summary`, список участий, статистика колод и история матчей должны описывать
один и тот же набор событий. В историю игрока не должны попадать матчи события,
которого нет в его списке участий текущего среза.

`summary.isSmallSample` должен соответствовать общему правилу интерфейса:
достаточная выборка начинается с 20 известных матчей, включая BYE, минимум в
5 турнирах.

### Любимый формат

Нужны:

- `format`;
- `matchesCount`;
- `tournamentsCount`.

Правила:

- учитывается вся доступная карьера игрока;
- главным показателем является количество известных матчей, включая BYE;
- при равенстве учитывается количество турниров, затем название формата;
- dashboard-фильтр `formatId` не должен превращать любимый формат в заранее
  известное значение;
- если данных нет, возвращается `null`.

### Любимая колода

Нужны:

- `deck`;
- `matchesCount`;
- `tournamentsCount`;
- доля известных матчей игрока на этой колоде.

Главным показателем является количество известных матчей, затем количество
турниров и название колоды. BYE участвует, если для него известна колода.

### Самый частый оппонент

Нужны:

- `player`;
- `matchesCount`;
- `wins`;
- `losses`;
- `draws`;
- `winRate`.

Правила:

- учитываются только матчи с реальным оппонентом;
- BYE не участвует;
- главным показателем является количество личных матчей;
- при равенстве учитываются победы, затем имя и `id` оппонента;
- если данных нет, возвращается `null`.

### Матчи и BYE

В summary игрока нужны отдельные поля:

```json
{
  "matchesCount": 0,
  "playedMatchesCount": 0,
  "byesCount": 0,
  "unknownResultsCount": 0
}
```

Требования:

- `playedMatchesCount` считает только матчи с реальным оппонентом;
- `byesCount` считает BYE;
- BYE входит в `matchesCount` и `matchWins`;
- неизвестные записи не входят в `matchesCount`, record и процент побед;
- одинаковые определения используются во всех ответах API.

## Приоритет 4. История матчей игрока

История матчей должна загружаться страницами.

Ожидаемый запрос:

```http
GET /api/v1/players/{id}/matches?page=1&page_size=50
```

Требования:

- поддерживаются общие dashboard-фильтры;
- ответ содержит `count`, `next`, `previous`, `appliedFilters` и `results`;
- в `results` находятся матчи с реальным оппонентом и BYE;
- строки содержат событие, клуб, раунд, стол, обе колоды, оппонента, счёт,
  результат и признак BYE;
- для BYE `opponent` равен `null`, а `isBye` равен `true`;
- если `opponent` равен `null`, а `isBye` не равен `true`, запись считается
  неизвестной и не участвует в расчётах;
- по умолчанию сначала показываются новые события и поздние раунды;
- между страницами нет повторов и пропусков;
- пагинация истории не меняет summary и insights игрока.

Большие списки турниров и колод игрока также должны поддерживать пагинацию:

```http
GET /api/v1/players/{id}/tournaments
GET /api/v1/players/{id}/decks
```

Оба списка принимают общие фильтры, возвращают `count`, `next`, `previous` и
`results`, сортируют всю выборку и не меняют summary или insights игрока.

## Приоритет 5. Серверная сортировка списков

Пагинированные списки должны сортироваться целиком, а не только внутри одной
страницы.

Общие параметры:

```text
sort=<field>
order=asc|desc
```

Нужные поля сортировки:

| Список | Поля |
|---|---|
| Турниры | `date`, `title`, `playersCount`, `roundsCount`, `matchesCount`, `winnerName` |
| Игроки | `name`, `tournamentsCount`, `matchesCount`, `matchWins`, `matchWinRate`, `bestRank`, `mostPlayedDeck` |
| Колоды | `name`, `format`, `tournamentsCount`, `playersCount`, `matchesCount`, `matchWins`, `matchWinRate`, `bestRank` |

Требования:

- одинаковый запрос всегда возвращает стабильный порядок;
- соседние страницы не содержат повторов и пропусков;
- неизвестное поле сортировки возвращает понятную ошибку `400`;
- `count` учитывает фильтры и поиск, но не пагинацию.

## Приоритет 6. Размер больших ответов

### Главная

`GET /api/v1/home` не должен возвращать сотни строк в секциях, где интерфейс
показывает только первые 10.

От backend нужны:

- summary по всей выборке;
- отдельные готовые highlights;
- не более 10 строк в превью-секциях.

Полные списки пользователь открывает на страницах турниров, игроков и колод.

### Страница колоды

В `GET /api/v1/decks/{id}` нужен объект `insights`, рассчитанный по всей
отфильтрованной истории колоды:

- доля всех участий в метагейме;
- самый активный игрок по количеству матчей, затем турниров;
- самый частый матчап;
- лучший и худший матчап только среди незеркальных матчапов с 10 или более
  матчами;
- количество матчей с известной и неизвестной колодой оппонента;
- динамика по месяцам: турниры, участия, матчи, победы, поражения, ничьи и
  процент побед.

Если подходящих данных для лучшего или худшего матчапа нет, соответствующее поле
равно `null`.

`summary.isSmallSample` должен соответствовать общему правилу интерфейса:
достаточная выборка начинается с 30 матчей минимум в 10 турнирах.

В `summary` также нужны отдельные значения реальных матчей и BYE. BYE не
участвует в record, winrate и матчапах.

```json
{
  "playedMatchesCount": 0,
  "byesCount": 0,
  "unknownResultsCount": 0,
  "matchesWithKnownOpponentDeckCount": 0,
  "matchesWithUnknownOpponentDeckCount": 0
}
```

Матч без названия колоды соперника остаётся сыгранным матчем, но не участвует в
сравнении матчапов. BYE и полностью неизвестный результат не должны попадать ни
в одну из двух групп матчей по известности колоды соперника.

Большие списки результатов, игроков и матчапов должны поддерживать пагинацию:

```http
GET /api/v1/decks/{id}/tournaments
GET /api/v1/decks/{id}/players
GET /api/v1/decks/{id}/matchups
```

Каждый список:

- принимает общие фильтры;
- возвращает `count`, `next`, `previous` и `results`;
- сортирует всю выборку;
- не меняет общий summary колоды;
- для матчапов использует статистику по всей выбранной выборке до пагинации.

## Что уже есть и не требует отдельной задачи

- общее количество сущностей уже приходит в `count`;
- поиск игроков и колод уже выполняется на backend;
- дейлики и турниры уже разделяются через `tournamentType`;
- существующие summary, record и winrate не нужно дублировать отдельными
  запросами.

## Не входит в текущую задачу

- API для дайджеста;
- лучший и худший личный winrate игрока против оппонентов;
- изменение действующего контракта добавления событий;
- выбор конкретной технологии, схемы базы данных или способа кэширования.

## Готово, когда

- [ ] Глобальные показатели не меняются после `Показать ещё`.
- [ ] Любимый формат и частый оппонент не зависят от страницы истории матчей.
- [ ] BYE отделены от матчей с реальным оппонентом.
- [ ] В турнире отдельно возвращаются паринги, реальные матчи и BYE.
- [ ] Колода участника совпадает во всех секциях ответа турнира.
- [ ] Детали турнира содержат исходную ссылку Aetherhub.
- [ ] История большого игрока загружается страницами.
- [ ] Сортировка применяется ко всей выборке.
- [ ] Между страницами нет повторов и пропусков.
- [ ] Главная не возвращает сотни строк для коротких превью.
- [ ] Большие списки на странице колоды можно загружать частями.

# Аудит недостающей статистики Magic Oculus

Состояние на **16 сентября 2026 года**. Аудит отвечает на вопрос: какую полезную
информацию можно показать сверх уже существующих экранов, не превращая продукт
в набор случайных графиков.

Зафиксированные решения по уже проверенным экранам находятся в
[SCREEN_REVIEW_CHECKPOINT.md](SCREEN_REVIEW_CHECKPOINT.md). Контракт и правила
источника истины — в [API_SOURCE_OF_TRUTH.md](API_SOURCE_OF_TRUTH.md).

## Короткий вывод

Magic Oculus уже хорошо показывает:

- объём турниров, игроков, матчей и колод;
- популярность и результативность колод;
- результаты игроков и историю выступлений;
- стендинги, раунды, метагейм отдельного события;
- личные встречи и матрицу матчапов;
- посещаемость дейликов и таблицы лиг.

Главные пробелы находятся не в количестве цифр, а в трёх вопросах:

1. **Что изменилось?** Сейчас почти все значения статичны и не сравниваются с
   предыдущим сопоставимым периодом.
2. **Насколько данным можно доверять?** Не хватает общей свежести, покрытия и
   полноты источника.
3. **Что из этого следует игроку?** Есть доля меты и отдельные матчапы, но нет
   компактного ответа, какие колоды растут, переоценены или хорошо подходят к
   ожидаемому полю.

Первый запрос к backend должен быть не «дайте ещё десять рейтингов», а
**свежесть + покрытие + сравнение периодов + non-mirror показатели**.

## Что уже приходит, но сознательно не выведено

| Данные | Где доступны | Решение |
| --- | --- | --- |
| `tournamentPlayersCount`, `uniqueDecksCount` | `/home` | Не добавлять ещё две крупные карточки. Можно использовать в строке контекста данных |
| `gameWins`, `gameLosses`, `gameDraws`, `gameWinRate` | профиль игрока | Полезно вторым уровнем в профиле, только вместе с числом известных игр |
| `bestRank`, `averageRank` | игроки и колоды | Не продвигать: сырое место несопоставимо между турнирами разного размера |
| `points`, `OMW`, `GW`, `OGW` | участия игрока и стендинги | Оставить в конкретном турнире; в общем профиле создают шум |
| `pairingsCount`, `byesCount` | турниры | Нужны для контроля полноты, но не как основные колонки списка |
| `sourceUrl`, `league` | турнир | Ссылку показывать в детали; лигу можно показывать компактным бейджем в списке |
| `bestRank` колоды в метагейме | главная и турнир | Не использовать как оценку силы без размера поля и числа участий |
| цвета и общий `archetype` | колоды | Дополнительное оформление и группировка возможны, но nullable-поля нельзя превращать в основу аналитики |

Эти поля не являются аргументом для автоматического расширения таблиц.

## Рекомендуемая новая статистика

### P0. Свежесть и покрытие данных

**Пользовательский вопрос:** насколько актуальна и полна показанная картина?

Backend должен возвращать общий контекст статистического ответа:

```ts
type DataContext = {
  generatedAt: string;
  dataUpdatedAt: string | null;
  latestTournamentDate: string | null;
  snapshotId: string;
  coverage: {
    tournamentsCount: number;
    tournamentParticipationsCount: number;
    knownDeckParticipationsCount: number;
    playedMatchesCount: number;
    matchesWithKnownOpponentDeckCount: number;
    unknownResultsCount: number;
    isComplete: boolean | null;
  };
};
```

Показывать это нужно одной компактной строкой рядом с фильтрами: «Данные по
12 сентября · колоды известны у 93% участий · матчап определён в 81% матчей».
Отдельный большой график не нужен.

Это важнее нового рейтинга: пользователь не должен принимать решение по
винрейту, не понимая, какая часть событий и колод известна.

### P1. Движение метагейма

**Пользовательский вопрос:** что стало встречаться чаще или реже?

Для текущего периода и непосредственно предшествующего периода той же длины:

```ts
type DeckTrend = {
  deck: DeckShort;
  current: {
    participationsCount: number;
    metaShare: number;
  };
  previous: {
    participationsCount: number;
    metaShare: number;
  };
  metaShareDelta: number;
};
```

На главной достаточно трёх строк: «быстрее всего растёт», «сильнее всего
снижается», «стабильный лидер». На странице колод — колонка изменения доли.
График нужен только в детали конкретной колоды: доля поля по неделям или месяцам.

Похожие MTG-сервисы делают период центральной частью анализа: MTGTop8 предлагает
срезы за последние дни, недели, месяцы и крупные события, а MTGGoldfish рядом с
долей меты показывает число наблюдений и свежие события.

### P1. Non-mirror record и процент побед

**Пользовательский вопрос:** как колода играет против остального поля, а не
против собственных копий?

```ts
type NonMirrorPerformance = {
  nonMirrorMatchesCount: number;
  nonMirrorWins: number;
  nonMirrorLosses: number;
  nonMirrorDraws: number;
  nonMirrorWinRate: number | null;
  isSmallSample: boolean;
};
```

Это лучший кандидат на замену общему винрейту в сравнении архетипов. Зеркала
тянут результат к 50% и не помогают выбрать колоду против поля. MTGO Spectator
прямо использует общий record и non-mirror winrate в обзоре метагейма.

Backend должен исключать зеркала по стабильному ID архетипа, а не по текстовому
названию на frontend.

### P1. Конверсия колоды в результат

**Пользовательский вопрос:** популярная колода действительно приводит к
хорошему финишу или её просто много?

Для Magic Oculus безопаснее использовать уже согласованное понятие полного
турнира без поражений и ничьих:

```ts
type DeckFinishConversion = {
  participationsCount: number;
  completedParticipationsCount: number;
  undefeatedTopsCount: number;
  undefeatedTopRate: number | null;
};
```

Досрочно выбывшие игроки не входят в числитель. Backend обязан знать число
запланированных раундов и полноту участия. В интерфейсе показатель должен идти
рядом с долей меты и non-mirror результатом, а не отдельной лидерборд-страницей.

Конверсия популярности в высокий результат используется другими аналитическими
сервисами как способ отличить «популярную» колоду от «успешной».

### P1. Изменение посещаемости и состава сообщества

**Пользовательский вопрос:** локальная сцена растёт и возвращаются ли игроки?

Для дейликов:

```ts
type CommunityActivity = {
  uniquePlayersCount: number;
  newPlayersCount: number;
  returningPlayersCount: number;
  repeatPlayersCount: number;
  retentionRate: number | null;
  previousPeriodUniquePlayersCount: number;
  uniquePlayersDelta: number;
};
```

Определения должны быть строгими:

- новый игрок — первое известное участие за всю доступную историю;
- вернувшийся — играл до предыдущего периода, отсутствовал в нём и появился в
  текущем;
- удержание — доля игроков предыдущего периода, сыгравших в текущем.

На экране дейликов достаточно одной компактной карточки «Игроки за период» с
тремя числами. Дни недели и декоративные графики не добавляем.

### P1. Последняя активность и честные топы игроков

Поддержка на frontend уже добавлена:

```ts
type PlayerListActivity = {
  lastTournamentDate: string | null;
  undefeatedTopsCount: number | null;
};
```

Backend должен вычислять `undefeatedTopsCount` только по полностью пройденным
турнирам без поражений и ничьих. `bestRank === 1` не является заменой.

### P2. «Насколько колода подходит к ожидаемому полю»

**Пользовательский вопрос:** если завтра поле будет похоже на выбранный период,
как эта колода выглядит против него?

Backend может взвесить non-mirror матчапы по текущей доле соперников:

```text
fieldScore = Σ(matchupWinRate(deck, opponent) × opponentMetaShare)
```

Возвращать нужно не только итог:

```ts
type FieldScore = {
  score: number | null;
  coveredMetaShare: number;
  coveredMatchesCount: number;
  missingOpponentDecksCount: number;
};
```

Если покрыто меньше согласованной доли поля, итог не показывается. Это полезный
ответ для подготовки к событию, но он не должен называться «прогнозом победы»:
он описывает только исторические матчапы и выбранную структуру поля.

### P2. Текущая форма игрока

**Пользовательский вопрос:** результат игрока стабилен или изменился недавно?

Вместо общего «тренда» без контекста backend должен вернуть два сопоставимых
окна, например последние 90 дней и предыдущие 90 дней:

```ts
type PlayerFormComparison = {
  current: MatchRecordWithSample;
  previous: MatchRecordWithSample;
  winRateDelta: number | null;
  lastTournamentDate: string | null;
};
```

Показывать одной строкой в профиле, только если оба периода проходят минимальную
выборку. Серии побед и поражений можно добавить позже как развлекательную
статистику, но не ставить выше record и размера выборки.

### P2. Игровой record игрока

`gameWins`, `gameLosses`, `gameDraws` и `gameWinRate` уже приходят. Их можно
показывать в профиле вторым уровнем под матчевым record:

```text
Матчи  31–18–2 · 62,7%
Игры   68–47–4 · 58,8%
```

Перед включением backend должен гарантировать полный счёт партий и отдельное
покрытие. Неизвестные игры не превращаются в нули.

### P2. Практичная информация в лиге

Таблица лиги уже показывает очки и зачтённые турниры. Полезнее нового графика:

- отставание от следующего места;
- худший зачтённый результат, который можно заменить;
- число оставшихся турниров лиги;
- сколько очков принесёт следующий результат после правила
  `bestTournamentsCount`.

Backend знает правила и должен вернуть готовый `pointsToNextRank`,
`replaceableTournamentPoints` и `remainingTournamentsCount`. Frontend не должен
повторять правила лиги.

### P3. Рейтинг силы игрока

Elo/Glicko может быть интересен локальному сообществу и используется трекерами,
но это отдельный продуктовый проект. До реализации необходимо решить:

- начальный рейтинг и порядок обработки событий;
- влияние ничьих, BYE и неизвестных результатов;
- разделение форматов;
- пересчёт после исправления старого события;
- минимальную активность и период неактивности.

Не добавлять «скрытый Elo», вычисленный frontend из текущей страницы.

## Размещение по экранам

| Экран | Что добавить | Как показать |
| --- | --- | --- |
| Главная | свежесть, покрытие, 2–3 изменения меты | строка контекста + компактный блок «Что изменилось» |
| Дейлики | уникальные, новые, вернувшиеся, удержание | одна карточка при выбранном срезе |
| Турниры | лига в строке; статус полноты импорта | бейдж и статус, без новых числовых колонок |
| Турнир | сравнение его меты с выбранным историческим периодом | только по явному действию «Сравнить с метой» |
| Игроки | последняя активность, полные топы без поражений | уже подготовлено, ждёт backend |
| Игрок | форма по двум периодам; игровой record при полном покрытии | одна строка + вторичный record |
| Колоды | изменение доли, non-mirror winrate, конверсия | три сопоставимые колонки с размером выборки |
| Колода | история доли, field score и покрытие | один график динамики + одна карточка пригодности к полю |
| Матрица | фильтр минимального числа матчей, свежесть среза | настройка матрицы и строка контекста |
| Лиги | отставание и заменяемый результат | в раскрытии игрока, не в общей таблице |

## Что не стоит добавлять

- среднее место без нормализации по размеру турнира;
- число первых мест как замену полным турнирам без поражений;
- винрейт без record, размера выборки и признака её достаточности;
- общий показатель по нескольким форматам;
- серии побед при неполной или непоследовательной истории;
- прогнозы, не показывающие покрытие матчапов;
- графики, которые повторяют одно число;
- новые frontend-агрегаты, если backend уже способен вернуть готовый результат.

## Предлагаемый порядок backend-работ

1. `DataContext`: свежесть, snapshot и покрытие во всех статистических ответах.
2. `lastTournamentDate` и `undefeatedTopsCount` в `/players`.
3. Non-mirror record для колод и матчапов.
4. Сравнение текущего периода с предыдущим: доля меты и посещаемость.
5. Конверсия колоды в полные турниры без поражений.
6. Новые, вернувшиеся и удержанные игроки для дейликов.
7. Field score с обязательным покрытием.
8. Форма игрока, league gap и только затем Elo/Glicko.

## Критерии приёмки новых агрегатов

- фильтры одинаково применяются к числителю, знаменателю и сравнению;
- предыдущий период той же длины и не пересекается с текущим;
- зеркала определяются серверным ID архетипа;
- BYE не считается сыгранным матчем;
- досрочно выбывший игрок не получает полный топ без поражений;
- у каждой доли есть числитель и знаменатель;
- отсутствие знания возвращается как `null`, а не `0`;
- малая выборка и покрытие приходят от backend;
- агрегат не зависит от пагинации списка;
- один экран не скачивает все строки ради одной карточки.

## Внешние ориентиры

- [MTGGoldfish Metagame](https://www.mtggoldfish.com/metagame) — доля меты
  всегда сопровождается числом колод и свежими событиями.
- [MTGTop8](https://www.mtgtop8.com/format?cp=1&f=ST) — анализ начинается с
  временного окна: последние дни, недели, месяцы и отдельные типы событий.
- [MTGO Spectator](https://mtgospectator.com/) — рядом показаны доля архетипа,
  record, non-mirror winrate, матрица и фиксированные снимки периода.
- [Magic4ever Tracker](https://www.magic4ever.com/tracker) — использует
  conversion rate, чтобы отличать популярность колоды от способности доходить
  до высокого результата.
- [17Lands](https://www.17lands.com/deck_color_data) — показывает победы,
  количество игр и winrate вместе, сохраняя знаменатель рядом с процентом.
- [Castlog Analytics](https://castlog.gg/features/analytics) — хороший источник
  идей для личного профиля: изменения winrate, head-to-head и серии; для Magic
  Oculus серии имеют более низкий приоритет из-за полноты данных.
